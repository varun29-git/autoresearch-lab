# Transferring optimizer tuning to a 1.5B model on 32 GPUs

**Date:** 2026-10-08. **Status:** proposed verification protocol, extending the [optimizer research](OPTIMIZER_TUNING_RESEARCH.md) and [HPO campaign plan](HYPERPARAMETER_AUTORESEARCH_PLAN.md). **Research uses one GPU; 32 GPUs are available only for eventual production.** No 32-GPU quality run or paid research campaign has been performed. “Transfer” below means a testable prediction for a **new run from initialization**, not copying a 100M checkpoint into a 1.5B model.

## The answer in one sentence

A correctly implemented µP-family parameterization can make **some per-role LR coordinates** approximately stable as **width** changes, but it does not determine the best **global batch, token horizon, weight decay, WSD schedule, QAT recipe, or hardware layout**. Thirty-two GPUs by themselves change only how the batch is split; if they cause a larger global tokens-per-update, batch-dependent hyperparameters need a separate bridge.

## Why “100M proxy” is not quite the same architecture here

At fixed 25 layers, 128-dimensional heads, three query heads per KV head, and FFN width `2.5 × d_model`, the selected stack has approximately the following parameter counts. The 200M row matches the [measured stack count](../notes/FINAL_REPORT_ARCHITECTURE_20261006.md); the other rows are calculated from the same tied-embedding and block shapes and need an instantiated-config check before campaign lock. The production DeepGEMM path also requires `ffn_dim` divisible by 128.

| Width | Q/KV heads | Approx. total | Tied embedding | Embedding share | Intended role |
| ---: | ---: | ---: | ---: | ---: | --- |
| 384 | 3/1 | **62.69M** | 25.17M | **40.1%** | **Hypothetical shape:** FFN `960` fails DeepGEMM's 128 alignment |
| 768 | 6/2 | **200.33M** | 50.33M | **25.1%** | Primary HPO proxy with prior quality receipt |
| 1536 | 12/4 | **700.48M** | 100.66M | **14.4%** | Width/LR bridge |
| 2304 | 18/6 | **1,500.46M** | 150.99M | **10.1%** | Final target geometry |

An approximately 100M model with this 25-layer, 128-head-dimension design would need a width between `384` and `768`, or a changed head ratio, head dimension, depth, or FFN expansion. Those are additional architecture changes. In fact, `d=384` with the exact `2.5×` FFN ratio gives `ffn_dim=960`, which the production FP8 kernel rejects. Rounding its FFN to `1024` gives about **64.53M** parameters and changes the expansion ratio; reference BF16 is another different numerical path. A smaller auxiliary model may cheaply reveal a numerical failure, but it cannot stand in for this exact production-width family, and its tied embedding dominates far more of its parameter budget. Keep **200M → 700M → 1.5B** as the main transfer chain.

## What transfers, under what contract

| Quantity learned at proxy | Scale rule or required check | Decision at 1.5B |
| --- | --- | --- |
| **Chosen mechanisms and parameter roles** | Keep 25-layer Peri-LN/value-residual stack, local/global pattern, tokenizer/vocabulary, 128 head dimension, 3:1 GQA, FFN ratio, FP8/ternary mapping, and role classification consistent. | These are experimental controls, not conclusions of µP. If one changes, start a new family and recheck its optimizer neighborhood. |
| **Hidden AdamW matrix LR, in a derived µP arm** | Tensor Programs V's Adam hidden-matrix rule suggests `η_g(d) = η_g(d0) × fan_in(d0)/fan_in(d)` for compatible matrices. From `d0=768` to `2304`, same-role fan-in triples, so the predicted **physical** hidden AdamW LR is one third. A role multiplier such as `2×` remains attached to that role. | Check initialization, update/activation scale and an LR sentinel at 700M and 1.5B. This rule does not apply to the current standard-parameterization model merely by setting a flag. |
| **Hybrid Muon matrix LR** | The current code uses `LR_g=η_base ×0.2√fan_in`, with upstream rectangular normalization; at 3× fan-in its physical group LR rises by `√3` if base LR is unchanged. The repo's `sqrt_fan_in_ratio` alternative adds `fan_in_base/fan_in`, so physical LR instead falls by `1/√3`. These are **competing empirical width rules** for this exact Muon implementation. | Keep the tuned **base** and per-role multipliers only if the 700M/1.5B sentinel loss ranking, update/activation ratios, spectral/logit scales, and stability overlap. Do not rename either rule “µP” without a complete parameterization and numerical check. |
| **Tied embedding/readout AdamW LR** | Tensor Programs V Table 8 motivates a particular tied-weight initialization and `1/r` readout multiplier with a width-constant base LR. Terminus currently initializes the tied matrix with width-dependent variance and has no such readout multiplier. Embedding share falls from 25.1% to 10.1% along the main bridge. | Recheck its own LR bracket at 700M and at least one neighbor at 1.5B; inspect input and logit effects and rare-token/domain loss. A small-model embedding winner is not automatically final. |
| **Norm/QK/value-residual LRs and AdamW betas/epsilon** | Width-constant vector/scalar LRs are a **starting hypothesis** only after forward/init scaling is specified. Betas and epsilon are update-rule settings, but gradient magnitude, FP8, and batch can change their effective behavior. | Transfer the values as a baseline, then check group update/function ratios, gain/logit/λ trajectories, and `√v̂/ε`. Reopen a local bracket on drift or QAT failure. |
| **Weight decay** | For decoupled decay, per-group cumulative shrinkage is `S_g=Π_t(1−η_g(t)λ_g(t))`. A µP-induced AdamW LR change can be paired with inverse WD scaling to preserve this *decay timescale*, as [Wang and Aitchison](https://arxiv.org/abs/2405.13698) suggest testing. The current Muon builder already divides matrix WD by its shape LR factor, so its default peak `LR×WD` is width-constant for a fixed base LR. | Record both nominal WD and cumulative shrinkage. Test local WD at final width/horizon; fixed shrinkage is a diagnostic control, not a proof of optimal regularization. |
| **Batch, warmup, WSD decay, QAT LR/state, clipping** | µP width transfer gives no automatic rule. Batch changes optimizer updates per token and momentum/decay timescales measured in tokens; horizon changes the best peak LR and schedule; QAT changes the objective. | Tune batch and its local LR neighborhood at proxy with enough **updates**, then verify at 700M/1.5B. Complete each declared schedule before ranking. Recheck QAT groups from matched dense parents. |

The original [µTransfer paper](https://arxiv.org/abs/2203.03466), Tables 1–3 and 8, provides the Adam width-scaling starting point, including tied readout handling. The [Muon width-transfer study](https://arxiv.org/abs/2505.02222), §3, holds depth, batch, steps, and data fixed while varying width and calibrates a narrowing LR/WD region at successive widths. The [horizon study](https://arxiv.org/abs/2409.19913) found optimal peak LR can shift with training duration even under µP. [GQA-µP](https://arxiv.org/abs/2605.15290) motivates spectral/logit checks in addition to coordinate RMS. These sources justify the **test design**, not a numerical 1.5B LR for this ternary-target model.

## What 32 GPUs do to the optimizer

For pure data parallelism, the update batch is

`B_tokens = microbatch_sequences_per_GPU × data_parallel_GPU_count × accumulation × context_tokens`.

The existing [trainer](../terminus/train.py) calculates tokens with `world_size`, scales the local summed loss so DDP averaging yields a global token-mean gradient, clips after gradient synchronization, then applies the optimizer. Thus **if** the same model, data batch, parameter groups, numerical path, and global `B_tokens` are used, moving the update from one GPU to 32 data-parallel GPUs requires **no mathematical LR multiplier**. Floating-point reduction order and kernel behavior may differ; multi-rank gradient/update parity is a **later production-cluster gate**. All optimizer-quality comparisons below use one GPU with accumulation to reproduce the proposed global batch.

| Global batch at 4096 context | One-GPU 200M: micro × accumulation | One-GPU 1.5B: proposed micro × accumulation | Later 32-data-parallel-GPU equivalent | Updates for 0.5B / 2.5B / 10B tokens |
| --- | ---: | ---: | ---: | ---: |
| **393,216 tokens** | `32 × 3` | `8 × 12` | `3 × 1` | ~1,272 / 6,358 / 25,431 |
| **2,097,152 tokens** | `32 × 16` | `8 × 64` | `8 × 2` | ~238 / 1,192 / 4,768 |

The second batch is **5.33× larger**. Its 0.5B screen sees only ~238 optimizer updates, about ~119 in a 250M-token warmup; it cannot rank close LR or momentum choices. At equal training tokens, any per-update EMA with beta `β` spans roughly `B_tokens/(1−β)` tokens, and decay gets approximately `5.33×` fewer applications if LR and WD schedules are unchanged. A proposed final batch near 2.1M therefore needs its **own** LR, WD, momentum/beta, clipping, and WSD neighborhood. Use 0.5B only for safety; compare promising batches on completed, longer **single-GPU** proxy schedules (for example, 10B gives ~4,768 updates at 2.1M) and a single-GPU target-width sentinel. Research can establish the quality-safe batch region now; when production hardware exists, benchmark its 32-GPU tokens/s/GPU-hours before choosing the cost optimum. The older 2.1M target was a **single-GPU systems benchmark setting**, not a measured quality optimum for the selected architecture. The microbatch decompositions in the table require native fit/throughput checks; an equivalent product may be substituted without changing `B_tokens`.

The current trainer has replicated DDP, not FSDP/tensor/pipeline parallelism; CUDA graph capture is restricted to one GPU. If the eventual “32 GPUs” includes tensor or pipeline parallelism, use the **data-parallel degree**, which may be less than 32, in the batch equation. For Muon, reduce the **full logical Q/K/V and FFN matrices' gradients** before Newton–Schulz, as replicated DDP does. Applying Muon separately to arbitrary tensor or optimizer shards changes the optimizer. A 32-GPU sharded implementation needs a tested full-logical-matrix update contract and a new runtime version. The resume contract includes `world_size` and per-rank RNG state, so changing from one to 32 ranks is a new run or an explicit checkpoint-migration project, not a transparent resume. Multi-node/32-GPU throughput, communication, preflight, and resume are **deferred production launch checks**, not prerequisites to the single-GPU research loop.

## The promotion test, in order

1. **Choose and freeze the scale family.** Prefer `d=768/1536/2304`, depth 25, fixed head/FFN/GQA geometry. Specify one complete parameterization ID per optimizer arm: initialization, forward multipliers, hidden/embedding/norm role LR width formulas, decay convention, and dense/ternary effective-weight path. The current parameterization is the control; a tied-readout µP arm is a new recipe trained from initialization.
2. **Calibrate at 200M.** Find an **interior** near-optimal region for Muon hybrid and all-AdamW separately on a full 2.5B decay, at one fixed batch and data distribution. Early checkpoints only reject failures. Preserve rate neighbors and group diagnostics rather than transferring a single winning decimal.
3. **Test width while holding other axes fixed.** At 700M, train the transferred winner plus a lower and higher sentinel rate on the same 2.5B horizon, batch, data, and schedule. At 1.5B, check the transferred candidate and at least one neighbor. Coordinate RMS, effective updates, spectral/logit behavior, cumulative shrinkage, and *loss ranking* should agree sufficiently. If they do not, retune that role or width rule locally; the proxy did not deliver reliable transfer for it.
4. **Test the intended production global batch on one GPU.** Match `B_tokens` with gradient accumulation; compare it with at least one neighbor and use a local LR/WD/beta check at each batch. At 2.1M tokens/update, require a completed horizon with thousands of updates before declaring quality. Use single-GPU H100 numerics, memory, throughput, failures, and exact resume now. Verify 32-rank mean-gradient and Muon full-logical-matrix equivalence, communication, throughput, and multi-rank resume only when the production cluster is available.
5. **Bridge the real training duration and ternary phase.** Fit a duration trend only from at least two **fully decayed** proxy horizons and a target-width bracket; a 2.5B or 10B pilot cannot prove a 1.5T-token peak LR. Lock a 1.5B full-run schedule against representative multilingual data and a declared token/compute budget. Run matched dense→ternary pilots with QAT-specific rates before committing the production recipe. Keep an untouched final evaluation set.

The practical deliverable is a **transfer interval with evidence**: a base role-rate vector at 200M, width formulas, a target-batch policy, 700M/1.5B sentinel losses and scale diagnostics, a longer-horizon correction, and QAT confirmation. If the sentinel points disagree, the correct result is a local target-scale tune, not a claim that µP transferred.
