# Short measurement first; deeper checks for winners

For the first screen, use the **full optimizer update** from `terminus.train.PreparedTraining.complete_update()`: real batches and H2D, all accumulation microsteps, forward, loss, backward, clipping, Muon/Adam and FP8 cache invalidation. `scripts/s0_block.py` wraps a block of updates with CUDA synchronization. The callback reports valid targets and elapsed seconds. It never times only a forward pass.

Run one or two warmup updates, then 2–5 measured updates per arm at the same 1.5B shape, microbatch and phase. If one update itself is long, use fewer; if an update is very short, use enough to get a stable block of roughly 20–60 seconds. Keep the workload identical between reference and candidate. Report the **measured block time and the entire billed VM time separately**. Compilation, VM boot and checkpoint/archive work are real costs, but they need not be repeated inside every timing block.

The short research timer omits the broad production preflight and does not save a full model/optimizer checkpoint by default. That is deliberate: those operations cannot improve the answer to “how fast is one optimizer update?” A candidate that fails a full update is recorded as a failure. CPU shape/reference tests and one native sanity update are enough to begin screening. Run the production preflight and deeper native gradient checks when a changed kernel is a serious finalist. The normal `run_training` path still requires its original native preflight.

A large clear gain can be kept for more testing after one short comparison. Repeat close results. Do not claim a marginal gain from noise; do not spend twelve minutes proving that a poor idea loses. Preserve the model computation: 25 layers, Peri-LN gains, V₁ gradient path, Q/K gains, attention masks, tied head, optimizer and token stream. If a finalist changes numerical precision, compare gradients and matched-token held-out quality in dense and QAT. Before a production recommendation, check sustained speed, memory, checkpoint/resume and real 32-GPU scaling. Those deeper tests are **not prerequisites for an initial throughput number**.

The human launches and stops the research VM. The Azure speed worker is intended to archive and verify results, then request deallocation. Do not leave the H100 idle while designing the next experiment. If its shutdown path has not been tested, explicitly confirm the VM is off through the human's controller. A failed archive needs recovery, not an assumption that the VM is off.
