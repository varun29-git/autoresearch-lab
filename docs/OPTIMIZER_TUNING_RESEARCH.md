# Optimizer tuning for the 200M → 700M → 1.5B Terminus scale family

**Research date:** 2026-10-08. **Status:** proposed `hpo/v1` protocol; no paid training authorized or run. This is a companion to [the HPO campaign plan](HYPERPARAMETER_AUTORESEARCH_PLAN.md), [the single-GPU test matrix for eventual 32-GPU production](HPO_TEST_MATRIX_32GPU.md), [the 32-GPU scale-transfer note](OPTIMIZER_SCALE_TRANSFER_32GPU.md), and [the public group-implementation review](HPO_OPTIMIZER_GROUPS_RESEARCH.md). Every number below is either a measured Terminus control, a published result with its own optimizer convention, or a **proposed test point**. None is a measured 1.5B optimum.

## Answer and the evidence behind it

**Tune a hybrid Muon plus AdamW recipe and a fully tuned all-AdamW control as separate arms.** Within each arm, find a safe global matrix LR region at 200M, then tune the tied embedding, norms and Q/K gains, and only then test physical matrix-role multipliers. Verify promising rates on a completed decay, at 700M, at the 1.5B target, on a longer token horizon, and after ternary QAT. A 0.5B-token checkpoint is a safety and gross-ranking signal, not a final optimum. An optimizer win must survive matched tokens, measured GPU-hours, and final ternary quality.

The reason for explicit groups is empirical, not just aesthetic: [Apple's per-module AdamW study](https://arxiv.org/abs/2512.22382), §§3.1–3.3 and Fig. 1, found that most of its gain came from module-type rates, with a smaller gain from depth multipliers. Its optimized recipe transferred from roughly 50M/1.6B-token proxies to roughly 1.3B/26B-token runs and reported a **27% speed-up to the same loss** in its setting. It used about **5,000 proxy trials**, a different parameterization, cosine schedule, data, and model; that result motivates a *small, measured* role search here, not a promise of 27% for Terminus. The paper also found uneven, interacting stability boundaries; an exhaustive grid or unconstrained random search is a poor use of this budget. Its trust-region search in log-LR space is a useful conditional method once a stable incumbent exists.

The [completed architecture trial](../notes/FINAL_REPORT_ARCHITECTURE_20261006.md) tested **one** optimizer recipe: Muon base `0.003`, tied embedding/readout AdamW `0.003`, main/Peri/final norms `0.0002`, Q/K gains `0.0001`, WD `0.1` on matrices and embedding, batch `393,216` tokens/update, and 2.5B-token WSD. It reached English dense loss `2.65363`, then `2.81095` after a matched 500M-token QAT probe. Those rates are a stable control, **not** an LR optimization. A 150M archived run completed with Muon/embedding/norm rates all `0.01` but showed attention-gain collapse and residual drift; because three rates changed together, it establishes neither a good `0.01` recipe nor a safe upper bound for one group. See [the HPO plan](HYPERPARAMETER_AUTORESEARCH_PLAN.md#lr-range-audit-before-spending).

## Exact arms and group semantics

Keep the same chosen Peri-LN plus value-residual model, tokenizer, data order, precision, schedule, batch, seed, evaluations, and QAT implementation while comparing optimizer arms. Each arm gets its own LR/WD/beta tuning and width rule; sharing a literal peak LR would be an unfair control. Compare equal-token loss **and** measured GPU-hours, including optimizer overhead, memory capacity, validation, and checkpoint pauses. If all-AdamW needs a different device count or smaller microbatch to fit, report that cost explicitly and retain the same *effective* batch when testing optimizer quality.

| Arm | Hidden matrices | Other trainable parameters | Initial source of rates |
| --- | --- | --- | --- |
| **M: pinned hybrid** | Logical-slice Muon, currently base `0.003` and per-matrix physical LR `base × 0.2√fan_in`; upstream update also applies its aspect-ratio factor. Momentum `0.95`. | Adam update for tied embedding/readout, main/Peri/final norm, Q/K gains, value-residual scalars. The current [`build_hpo_optimizer`](../terminus/hpo_optimizer.py) exposes Muon physical-matrix and AdamW auxiliary roles without changing the architecture trainer. It does **not** yet support all-AdamW role overrides. [`build_optimizer`](../terminus/optim.py) can construct an all-AdamW baseline, but puts all hidden matrices in one group. Before an all-AdamW group campaign, add a behavior-preserving role split for that arm and check default one-step/resume equivalence. Both arms must assign each trainable parameter once. The tied `tok_embeddings.weight` is one physical matrix: no “input LR” and “output LR” can be set independently without a new model parameterization. Fused `qkv_proj` and `gate_up_proj` have one physical LR each today. Independent Q/K/V or gate/up rates require a separately tested slice-aware update; a label alone does not implement them.

The Muon wrapper performs **decoupled** decay on each logical matrix slice, and its auxiliary Adam code does likewise. With `s_g=0.2√fan_in`, the current matrix group uses `LR_g = η_M s_g` and `WD_g = λ/s_g`, giving a peak product `η_M λ`. A group LR override changes `LR_g × WD_g`, because the builder leaves WD fixed. In the all-AdamW arm, `LR_g=η_{A,g}` and, initially, `WD_g=λ_g`. For either arm, record the actual scheduled `LR_g(t)`, `WD_g(t)`, and cumulative **decay-only shrinkage**

`S_g = Π_t [1 − LR_g(t) × WD_g(t)]`, or `−log S_g = −Σ_t log[1 − LR_g(t) × WD_g(t)]`.

This product is a *decay diagnostic*, not a complete description of the trained weight, since gradients and weight scale also move. Require `0 ≤ LR_g(t)×WD_g(t) < 1` in the recipe resolver. First compare candidate **recipes** with fixed inherited WD, which answers which setting trains better. Then, if a role LR wins, run one **matched-shrinkage** counterfactual where `WD_new = WD_control × LR_control/LR_new` for that role (or the corresponding scheduled factor) to distinguish optimization-rate benefit from changed decay pressure. Search WD properly after the LR region; do not silently equate a copied λ with equivalent regularization across width, batch, or token horizon. At zero-WD norm/QK roles, this confound is absent.

### Search policy and decisions

1. **First establish a bracket in each arm.** Candidate rates are log-spaced and intentionally broad. A stable *interior* winner at completed decay, with worse neighbors beyond evaluation noise, justifies narrowing. An edge winner requires expansion; a nonfinite high point brackets safety, not the best quality. Track both absolute loss and learning-curve area, because a recipe can train fast early yet finish worse.
2. **Use sequential role tests around an incumbent.** Take one role's `0.5×/2×` points, or a small log-space trust region around a winner. After a clear role gain, compare the combined recipe with the best single-role recipe and one reversal/ablation to expose interactions. This adapts Apple's trust-region and module-type findings to a small budget; it does **not** pretend to reproduce its 5,000-trial optimizer. Fixed early/middle/late depth multipliers may be tested only after a consistent layerwise pattern; independently tuning 25 layers × every role is unjustified.
3. **Never infer a long-horizon optimum from a short prefix.** The first 0.5B of a 2.5B WSD run spans warmup and early stable training. Apple's Fig. 7 shows that optimal short schedules need not be prefixes of long ones; the horizon-LR study independently finds LR shifts with duration. Fully decay the promoted branch at its declared horizon. For a 10B or longer study, start a separate schedule from initialization and use fresh data; do not simply extend the already decayed 2.5B optimizer trajectory.
4. **Treat width transfer as a hypothesis test.** The base-width LR optimum may move because the tied embedding's relative parameter share changes, the FFN and GQA shapes change, and AdamW decay timescale changes. For all-AdamW hidden matrices, the Tensor Programs V Adam rule suggests `LR_g(d) ∝ 1/fan_in`; the [AdamW decay paper](https://arxiv.org/abs/2405.13698) suggests testing a compensating WD factor if the aim is fixed decay timescale. For Muon, compare the current `sqrt_fan_in` rule with the repo's `sqrt_fan_in_ratio` proposal as an **empirical** arm; do not call either one derived µP for this entire architecture. The tied-weight µP forward/init proposal and required coordinate gate are specified in [the HPO plan](HYPERPARAMETER_AUTORESEARCH_PLAN.md#3-parameterization-is-a-versioned-experiment-not-a-label).
5. **Keep optimizer quality and cost separate.** At equal tokens compare dense and ternary loss, per-domain/task results, incidents, throughput, memory, and `GPU-hours-to-loss`. Muon can win tokens but lose time if its kernel overhead or memory behavior dominates at a particular batch; all-AdamW can look cheap per step but need more steps. Compare both Pareto frontiers, with repeated seeds and paired document resampling for close finalists. Adaptive search makes a single post-selection confidence interval descriptive, not a formal guarantee.

### Telemetry and pass/fail gates

Record per physical role and, where implemented, per logical slice: effective LR and decay product; parameter RMS; gradient RMS; pre/post Muon orthogonalization update RMS; row/column norm dispersion; update/weight and update/activation ratios; AdamW `√v̂ / ε` distribution; clipping frequency; nonfinite and FP8 scale/overflow/underflow counts. Record residual/branch RMS by layer, Q/K gain and attention logit maxima/RMS/entropy by head, value-residual mixture coefficients, tied input/readout contribution to logits, validation loss by domain and token frequency, and QAT conversion shock/recovery. Some of these are expensive; sample fixed diagnostic batches and a declared interval rather than full-training traces. The sentinel must include at least one near-optimal and one bracket rate at 700M and 1.5B. If the LR ranking flips, if logit or activation scale diverges with width, or if effective shrinkage changes materially, recalibrate locally rather than asserting µTransfer.

Each trial manifest records optimizer implementation commit, logical-slice map, physical group table, parameterization ID, actual group LRs/betas/epsilon/WD, scheduler multipliers, batch and token/update arithmetic, data/eval hashes, seed, parent checkpoint if any, and estimated versus actual cost. Group layout changes require fresh checkpoints or a tested state migration. Freeze these definitions in a versioned `hpo/v1` policy; retain append-only receipts and unrun native-GPU gates. Published literature gives strong reasons to test these axes, but **only matched Terminus runs can choose the final Muon or AdamW recipe**.

**Conditional optimizer research after the baseline:** If a tuned Muon arm still shows large, repeatable per-row update-norm dispersion tied to worse loss, a separately versioned NorMuon arm has a direct mechanism to test. If attention-logit maxima become pathological at 1.5B despite Q/K norm, test QK-Clip in a separate paired Muon version. In both cases, first establish the signal on the existing optimizer, then check one-step math, logical fused-slice behavior, resume, memory/throughput, full dense loss, and QAT; do not fold an optimizer change into a role-LR trial. These are failure-led options, not first-wave branches or assumed improvements.
