# Kernel gate before hyperparameter autoresearch

**Planning date:** 2026-10-08. **Status:** proposed; no new GPU work authorized or started. The human launches and stops paid GPU work. This gate precedes the [single-GPU optimizer matrix](HPO_TEST_MATRIX_32GPU.md). It changes implementation only in a separately versioned campaign; the selected 25-layer Peri-LN plus learned value-residual model, data, and scoring stay fixed for comparisons.

## Why this gate comes first

Kernel choices determine memory fit and measured GPU-hours per token. They can also alter BF16/FP8 rounding, backward gradients, and optimizer updates. Changing the implementation midway through an LR sweep would make cost comparisons inconsistent and might require numerical recertification. A frozen, measured runtime is therefore an input to the HPO budget and trial lock.

The selected-stack branch already has an H100 NVL result, recorded in `trial/stack/004` commit `faace6f` and its `optimizations/README.md`. At **1.5B parameters**, batch **2**, accumulation **64**, context **4,096**, and short **synthetic** full training steps, the existing path reached **36,048 tok/s**. A combined prototype (block-boundary and value-mix fusion, fused head loss, batched Muon) reached **32,643 tok/s**, or **0.906×** baseline; adding CUDA graphs reached **31,179 tok/s**, and adding an FP8 head reached **31,096 tok/s**. Its reported GPU operator parity gates passed. The first-cut implementation is therefore **not** a candidate to wire into `terminus/` as a bundle. The short synthetic benchmark neither identifies which component caused the slowdown nor establishes real-data training quality. A separate earlier synthetic 1.5B stack measurement was **39,006 tok/s** under its own conditions; use matched measurements for decisions, not either number as a universal cost rate.

## Exact work order

| Gate | Work and comparison | Exit condition |
| --- | --- | --- |
| **K0. Freeze reference** | Bring the selected stack into a new kernel-development branch/campaign version without altering its math. Preserve the existing H100 receipt and pin GPU, driver, PyTorch/Triton/DeepGEMM/FA3 versions, config, precision, batch, and seeds. Reproduce a no-change whole-step baseline. | Same model and optimizer step; baseline time, peak allocated/reserved memory, and loss recorded. Any unexplained baseline shift is diagnosed before speed claims. |
| **K1. Profile** | Profile full forward, backward, optimizer, activation quantization, loss/head, kernel launches, and memory on the actual **25 × 2304** stack. Compare baseline and the existing combined prototype. Inspect GPU trace and per-operation times; distinguish launch gaps, redundant memory traffic, underfilled GEMMs, head recomputation, and graph capture overhead. | A ranked bottleneck list with measured wall-time share and a predicted whole-step gain for each candidate. The current README's explanations are hypotheses until this trace confirms them. |
| **K2. Isolate candidates** | Benchmark **one change at a time** against the same baseline: `out_norm_residual`, `block_boundary`, `value_mix`, head loss, batched Muon, activation caching, and CUDA graphs. Check candidate combinations only after individual effects are known. For the head, count forward/backward GEMM passes and Python tile-loop time. For FP8 head, a real DeepGEMM swap and its precision effect require a distinct experiment; quantize/dequantize alone is not the intended acceleration. | Whole-step tokens/s and memory, with repeated measurements and variance, for every candidate. Retain only gains that survive a matched full-step rerun; archive slower paths. No percentage is credited from a microkernel benchmark alone. |
| **K3. Shape and optimizer bridge** | Recheck survivors at **200M, 700M, and 1.5B**, 4,096 context, with the fixed **393,216-token global batch** where it fits. At 1.5B also measure microbatch/accumulation alternatives at the **same** global batch; test the contemplated 2,097,152-token batch separately. Measure both hybrid Muon and all-AdamW whole steps if both remain HPO arms. Measure dense FP8 and ternary QAT throughput/memory separately. | The chosen runtime fits with headroom at each required width/mode; all-in step speed and memory at the chosen microbatch are known. Reprice the HPO matrix from these receipts. An optimizer-specific speedup must not be attributed to the other arm. |
| **K4. Numerical and training gate** | For every retained replacement, compare eager/reference forward outputs, gradients (including Peri-LN gains and value-residual coefficients), logical Muon updates or AdamW updates, FP8 scales, and QAT quantizer behavior on identical inputs. Check 1/10/100 real-token updates, loss/stability trajectories, checkpoint/resume, and graph capture where used. At the **393,216-token** batch, 100 updates process **39,321,600 tokens per run**. A changed-precision head needs a separate matched dense/QAT quality comparison, beyond operator tolerance. | No unexplained functional drift, broken resume, unstable scales, or quality regression. Numerical tolerances and any expected BF16 difference are recorded before looking at results. Correctness alone does not establish an LR optimum. |
| **K5. Lock runtime** | Integrate only the passing, faster or materially memory-saving pieces behind explicit config flags in the selected-stack source. Record exact source/config/runtime hashes and the old-path fallback. Keep generated traces and raw receipts outside Git. | A new frozen runtime/campaign version and updated all-in cost table. If no candidate clears K2–K4, lock the existing tuned path and proceed to HPO without waiting for speculative optimization. |

K1–K3 are synthetic performance probes: **zero real training-data exposure**. The K4 100-update check is a numerical/stability gate, not a quality-ranked HPO branch. Its per-run data exposure is **39.3M tokens at the proxy batch**; paired baseline and candidate dense runs require **78.6M tokens** if both use 100 updates, with QAT or further variants priced separately. Synthetic tokens processed are reported in benchmark receipts but not counted as fresh training data. These checks consume GPU time, so the owner receives a cost estimate before launch. No 32-GPU allocation is needed for this research gate; owner-optimizer/NCCL changes wait for the production-cluster parity gate.

Use alternating baseline/candidate order and repeat enough full steps to bound timing noise. For a candidate to win, show a positive **all-in** gain beyond measured run-to-run noise or a memory reduction that enables a faster fitting microbatch, while passing K4. The current 1.5B **36,048 tok/s** baseline is only the matched comparator for the existing short prototype. Recalculate all Stage-I–IV GPU-hour estimates from the final real-data all-in receipts, including data loading, evaluation, checkpointing, QAT, and resume overhead. Keep optimizer math, dataset, tokenizer, schedule, and scorer fixed across each kernel attribution test.

The implementation branch for K0–K5 is separate from the immutable architecture campaign. The HPO campaign starts only after K5 records either a certified optimized runtime or the existing baseline runtime. A later kernel change opens a new campaign version and a small matched bridge before comparing its trials with earlier HPO results.
