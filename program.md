# Kimi K3: Terminus architecture autoresearch

You are the autonomous researcher for **stage one only**: discover a shortlist of better Terminus architectures. Read this file, `README.md`, `SOURCE_BASELINE.md`, `research/policy.json`, `candidate.json`, and the maintained model code before the first experiment. Read the completed dense/QAT run analysis and archived test evidence. Consult relevant papers and open implementations as hypotheses arise. You choose the ideas; this program does not prescribe architectural mutations.

The human starts a paid campaign by opening this repository on the GPU machine and supplying a prepared campaign JSON. Once `python prepare.py --campaign /path/to/campaign.json` passes, run autonomously until the campaign's GPU-hour cap, a genuine blocker, or the human's stop instruction. Do not start a VM, build datasets, modify S3 source data, or begin a full-scale training run yourself. Do not ask after every experiment. If preparation fails because the dataset or benchmark suite is missing, report the specific missing input; do not substitute synthetic data or English-only tasks.

## The experimental contract

The frozen 65K tokenizer, prepared raw-document splits, ten-domain held-out data, answer-only task manifest, dense FP8 arithmetic, optimizer policy, batch, sequence length, WSD schedule, score definition, and budget are fixed by `research/policy.json` and the campaign lock. They are controls for this campaign, not assertions that these settings are globally optimal. The editable candidate is `candidate.json` and `terminus/model.py`. A new architecture may add `terminus/architecture_*.py` modules and matching `tests/test_architecture_*.py` tests. Existing quantization and kernel implementations are protected: low-level performance engineering is stage three, and QAT quantizer selection is stage two. If a scientific idea needs a protected data, loss, optimizer, quantizer, kernel, or evaluation change, record it for a **new campaign version**; do not quietly change this campaign's yardstick.

Each trial must remain within the stated parameter envelope. Compare candidates on the **same full-horizon schedule and token stream**. The screen ends after roughly 0.5B tokens, but is a checkpoint of a 2.5B-token schedule, not a separately decayed short run. The full stage resumes exactly from that checkpoint. The wall-clock limit is a safety cap, not the quality objective. Native SM90 numerical preflight runs for each distinct candidate before training.

The primary measurement is held-out next-token loss for English, seven Indic languages, code, and math. The protected scorer expresses each group's relative change from a matched-horizon baseline and applies predeclared group weights. Inspect every domain, not just the aggregate. The full stage also runs answer-only development tasks and fixed position-bucket diagnostics. Task accuracy at this proxy scale can be noisy; raw rationale imitation is not a success metric. A screen-only gain, one seed, or a tiny aggregate difference does not establish a final architecture. Stage one ends with a **shortlist and evidence**, not a claim that the eventual ternary model's architecture is solved.

## Research loop

1. Establish the unmodified baseline. Create a fresh `autoresearch/<tag>` branch, run preparation, then run `python train.py --campaign /path/to/campaign.json --trial-id baseline --stage screen` and `--stage full`. Read the validation trajectory and stability records, not only the final summary. The baseline full run is necessary for full-stage comparisons.
2. Before proposing a candidate, inspect the current architecture, the most informative prior trials, and at least one relevant primary source or implementation. Write a concise hypothesis in the experiment commit message: proposed mechanism, expected benefit, likely failure signal, source, and why it is applicable to Terminus. You may discover ideas from observations rather than a predetermined list. Prefer an interpretable change first; combine changes only when previous evidence identifies an interaction.
3. Create a separate `trial/<tag>/<number>` branch or worktree from the current incumbent. Modify only the editable surface. Run focused CPU tests, inspect the diff, and commit the candidate. Never modify the protected scorer or prepared data to improve a result. Do not install an unpinned package during an active campaign.
4. Run `python train.py --campaign /path/to/campaign.json --trial-id <number> --stage screen`. The runner writes logs, checkpoint receipts, and an append-only ledger outside Git. Read `python -m research.loop status --campaign /path/to/campaign.json`, the trial's train/evaluation logs, and the stability/incident files. A crash is a recorded outcome; fix a trivial implementation error with a new commit and a new trial ID.
5. Continue promising **or uncertain** screens with `--stage full` on the exact same candidate commit. The baseline and candidate must be compared at the same stage. A candidate with a clear domain regression needs a compelling task-level reason to remain on the frontier. Near ties are unresolved, not automatic wins. If the change affects model arithmetic or attention behavior, check native/reference parity and the relevant length-boundary tests before interpreting quality.
6. Keep an append-only evidence trail. Retain rejected branches and receipts; do not reset away failed experiments or rewrite published commits. Advance the incumbent only after a full comparison that survives review of all domains, tasks, stability, parameter count, and implementation complexity. Keep a small Pareto shortlist when trade-offs or uncertainty remain. After several unproductive ideas, step back, read the failures and literature, and form a new mechanism-based hypothesis.
7. Stop at the GPU-hour cap or if the remaining budget cannot support a meaningful continuation. Report exact completed trials, GPU-hours, missing benchmarks, and the shortlist with uncertainty. Recommend which finalists need a larger-width and ternary-QAT transfer check in stage two. Do not silently turn stage one into optimizer tuning or kernel optimization.

## Operational rules

- All full evaluations use the prepared development task suite. An untouched final suite remains outside the loop. Do not tune on it.
- Record citations or repository revisions for borrowed methods. Distinguish an established paper result from a Terminus hypothesis. Verify licenses before importing code.
- The model source may span multiple files, unlike Karpathy's `train.py`. The protected `train.py` here is a runner wrapper; the agent-editable architecture is `candidate.json` and the permitted model files.
- A fixed-time five-minute trial would reward speed and change the number of tokens seen. That is the wrong primary comparison for this quality-focused stage. Record time and memory, but do not declare an architecture better solely because it processed more data in the same time.
- The campaign has a hard spending cap. When the human asks to stop, stop. Archive every trial's logs and accepted checkpoints and verify the remote copies before allowing the GPU machine to shut down. Do not claim remote safety from a successful upload command alone.
