# Kimi K3: Terminus architecture autoresearch

You are the autonomous researcher for **stage one only**: discover a shortlist of better Terminus architectures for a **two-stage model: dense FP8 pretraining, then ternary-weight QAT with FP8 activations**. Read this file, `README.md`, `SOURCE_BASELINE.md`, `research/policy.json`, `candidate.json`, and the maintained model code before the first experiment. Read the completed dense/QAT run analysis and archived test evidence. **Find the papers and open implementations you need yourself as hypotheses and trial results arise**; neither this repository's references nor the human's suggestions are an exhaustive reading list. You choose the ideas; this program does not prescribe architectural mutations.

Run this research session on the **inexpensive controller**, not the H100. The human supplies a prepared campaign JSON, the staged English data and the Azure-cycle configuration, and launches the paid campaign. After that launch and the data gate pass, use [the Azure experiment cycle](docs/AZURE_EXPERIMENT_CYCLE.md) to start the existing H100 for **one committed experiment at a time**. The worker verifies checkpoints and every log in Blob before it deallocates the VM. Analyze, research, code and write diagnostic reviews only after the VM is off. Stay within both the protected campaign GPU-hour cap and the controller's VM-on budget. Do not create another VM, build datasets, modify S3 source data, or begin a full-scale training run. Do not ask after every experiment. If preparation fails because the English proxy data is missing, report the specific missing input; do not substitute synthetic data. An English task manifest is optional for this architecture stage.

## The experimental contract

The frozen 65K tokenizer, prepared English training/held-out split, optional English development tasks, FP8 arithmetic, optimizer policy, batch, sequence length, WSD schedule, score definition, and budget are fixed by `research/policy.json` and the campaign lock. They are controls for this campaign, not assertions that these settings are globally optimal. The editable candidate is `candidate.json` and `terminus/model.py`. A new architecture may add `terminus/architecture_*.py` modules and matching `tests/test_architecture_*.py` tests. **Any architecture mechanism is in scope except the explicitly excluded repeats below**: replace or reorganize substantial parts of the model, port a licensed method from a state-of-the-art implementation, or invent a new one. The size of a code change is not a rejection criterion. Keep each candidate inside the campaign's parameter and cost envelope; that is a comparison control, not a ban on major structural changes. Existing quantization and kernel implementations are protected: low-level performance engineering is stage three, and QAT quantizer selection is stage two. If a scientific idea needs a protected data, loss, optimizer, quantizer, kernel, or evaluation change, document the necessary **new campaign version**; do not quietly change this campaign's yardstick.

Each trial must remain within the stated parameter envelope. Compare candidates on the **same full-horizon schedule and token stream**. The screen ends after roughly 0.5B tokens, but is a checkpoint of a 2.5B-token schedule, not a separately decayed short run. The full stage resumes exactly from that checkpoint. The wall-clock limit is a safety cap, not the quality objective. Native SM90 numerical preflight runs for each distinct candidate before training.

Treat **architecture-side systems engineering** as part of this stage: count attention and MLP operations, projection/GEMM shapes and H100 tile alignment, FP8 casts, tensor traffic, activation/KV memory, local/global context cost and the number of serial kernels. Predict how those costs change at 1.5B and during ternary QAT. Then check the whole-step measured speed, memory and sampled GPU duty/power against the prediction. A faster architecture that learns worse and a better-learning one that is much slower are both tradeoffs; compare quality at equal tokens **and** the cost to reach useful quality. Investigate unexplained slowdowns or low GPU duty before promoting a design. Low-level kernel rewrites remain stage three, but a hardware-hostile architecture is a stage-one concern.

**English is the inexpensive stage-one architecture proxy.** Do not train and evaluate every candidate across Indic, code and math. Keep the tokenizer, English documents and held-out blocks identical across candidates. English quality is useful for finding general architectural mechanisms, but cross-domain transfer is a hypothesis, not a theorem; test only the shortlist on the wider production mixture later. An optional English answer-only development set can add a task signal, but its absence does not block the first campaign. Fixed position-bucket loss diagnoses behavior across the 4K context; it is not a long-context retrieval benchmark.

Do not reduce “better architecture” to final loss. Review separate axes at matched token exposure: **quality** (English held-out loss and tasks if supplied); **optimization efficiency** (the held-out learning curve and area under loss versus tokens); **stability** (nonfinite incidents, gradient clipping, layer/residual/attention and FP8 telemetry, late loss regression); and **systems cost** (training tokens/s, GPU-hours, peak memory and parameter count). Quantization robustness is a fifth, conditional axis measured with the QAT probe below. The status command retains named tensor statistics, training phases, position buckets and optional per-item task results rather than just maxima. Inspect **every material positive and negative signal** in context: layer, tensor, token phase, baseline difference, expected mechanism and possible confound. A numerical direction is not intrinsically beneficial; e.g., lower attention entropy can mean sharper useful retrieval or harmful collapse. A screen-only gain, one seed, or a tiny difference does not establish a final architecture. Stage one ends with a **Pareto shortlist and evidence**, not a claim that the eventual ternary model's architecture is solved.

The default experiment is **dense FP8 only**. Do not run QAT merely because the final model is ternary. A change that affects ternary representability, the distribution or scaling of weights/activations, the dense-to-QAT parameter mapping, or conversion stability may change the architecture ranking after quantization. When existing theory, published results, and Terminus diagnostics give a concrete reason to expect that, run the protected, matched `qat_probe` on the baseline and that candidate, starting from their completed dense full checkpoints. The probe uses the same continuation stream, FP8 activations, fixed ternary quantizer and a fixed half-rate WSD recipe; it records immediate conversion loss and loss after a short continuation. It is **diagnostic**, not a final QAT-duration or 1.5B-quality result. If the evidence does not identify a quantization-sensitive mechanism, skip QAT and say why. The QAT probe and its evaluation count toward the same GPU-hour cap.

## Standard for a serious architecture proposal

Before coding, write a short `notes/<trial>.md` following [the candidate note template](notes/TEMPLATE.md). For a borrowed method, identify the primary paper, the exact public implementation revision, the measured result and its hardware/model conditions, and the code license. For an original method, anchor the proposal in specific measured Terminus behavior and a related empirical result or a reproducible cheap diagnostic. A paper result on another model is **prior evidence**, not proof for Terminus. Every substantial proposal needs both a mathematical mechanism and empirical motivation; interesting-sounding names are insufficient.

State the forward equations and tensor shapes; normalization axes and epsilons; residual, attention and initialization scales; causal and positional behavior; and which parameters receive gradients. Derive the expected effect on variance, attention logits, gradient/update scale, parameter count, training FLOPs, activation memory, prefill/decode FLOPs, KV-cache bytes per token and dense-to-ternary error where relevant. Specify exactly how FP8 operand quantization and later ternary weights interact with the design. For a large coherent redesign, explain why its components must move together and what smaller control or diagnostic could separate their effects. Provide a predeclared prediction for English held-out learning, stability, systems cost and QAT sensitivity, including a falsifying outcome. Implement a simple reference path and test shapes, causality, gradients and native/reference numerical agreement before paying for training.

## Autonomous literature search

Research is part of **every proposal and diagnostic review**, performed on the inexpensive controller while the H100 is deallocated. Begin with a specific question raised by the model code, archived experiments, or a measured trial signal. Search for relevant primary papers, technical reports, ablations, and public implementations using available web/search tools and scholarly indexes (for example arXiv, OpenReview, ACL Anthology, conference proceedings and official project repositories). Choose search terms and follow citations or code links yourself. Search beyond references already present in this repository and beyond papers named by the human. Do not fill a paper quota or browse without a decision question.

For a substantial proposal, seek the strongest supporting evidence, a plausible competing method, and contrary or negative evidence. Read the source far enough to verify the equations and the claimed result, rather than relying on an abstract, search snippet or secondary summary. Check model width/size, data, token budget, precision, optimizer, evaluation metric and hardware before transferring a finding to Terminus. Pin the implementation revision and check its license before borrowing code. Record the query, source URL/identifier, access date, relevant section/table or code path, and what was learned in the trial note. Separate published measurements, mathematical argument, Terminus measurements, and untested predictions. If a source is unavailable or no close prior work exists, say so; an original idea may still proceed with a derivation and a cheap, reproducible diagnostic. Never invent a citation or imply a result was verified when it was not.

After a surprising gain, regression, instability or throughput result, search again for explanations and counterexamples **before** choosing the next experiment. Turn the findings into a concrete mechanism, predicted tensor-level signal and falsifying test within the fixed campaign controls. The search may reject a proposed trial without spending GPU time. Keep search and analysis off the H100; an open VM is for the committed experiment only.

## Previously tried designs: do not repeat

Do **not** spend a trial on `qk_norm_mode="unit_rms"`, the old gain-free Q/K RMS normalization with fixed attention scale. It has already been exercised in Terminus, including a 30B-token archived run. It bounded observed attention logits, but there is no matched evidence that removing learnable attention scale improved quality. Repeating that exact fixed-unit choice in this scarce overnight search would be **stupid use of GPU time**. The runner rejects that candidate setting. Do not hide the same operation inside `terminus/model.py` under another name.

Do **not** restore the old parameter-free, forced-unit SubLN/branch-normalization stack or add more unit-scale protection layers merely because they appear safer. The baseline explicitly disables SubLN. Propose a genuinely different normalization mechanism only with a specific expressivity/stability hypothesis and a comparison against the current baseline. Standard learned-gain pre-attention, pre-FFN and final RMSNorm are **not** excluded; neither are learned-scale Q/K normalization or no Q/K normalization. Treat the old learned-affine Q/K gain runaway as a separate risk to monitor, not as evidence that fixed-unit Q/K is optimal. See the [prior-design evidence](docs/EXCLUDED_UNIT_NORMALIZATION.md).

## Research loop

1. Establish the unmodified **screen** baseline. Create a fresh `autoresearch/<tag>` branch on the controller, commit it, inspect the deallocated VM with `python -m research.azure_cycle inspect --config /path/to/azure_cycle.json`, then invoke `python -m research.azure_cycle run --config /path/to/azure_cycle.json --trial-id baseline --stage screen`. The cycle stages the commit, prepares the locked campaign on the VM, runs the trial, independently verifies the Blob archive and deallocates. Read the downloaded validation trajectory and stability records, not only the final summary. Do not spend the baseline's remaining 2B tokens before seeing candidate screens.
2. Inspect the current architecture and the most informative prior trials, then independently search relevant primary sources and implementations using the autonomous literature-search protocol above. Produce the mathematical and empirical proposal note above, including the search trail and contrary evidence. You may discover ideas from observations rather than a predetermined list. A large, coherent architecture package is allowed when its parts have a joint rationale and enough prior evidence to justify the GPU cost; do not force it into cosmetic one-variable changes. Name the mechanism, expected benefit, likely failure signal, source, and why it applies to Terminus in the experiment commit message.
3. Create a separate `trial/<tag>/<number>` branch or worktree from the current incumbent. Modify the editable architecture surface, including any new architecture-specific modules and tests. Run focused CPU tests, inspect the diff, and commit the candidate and its proposal note. Never modify the protected scorer or prepared data to improve a result. Do not install an unpinned package during an active campaign.
4. Run `python -m research.azure_cycle run --config /path/to/azure_cycle.json --trial-id <number> --stage screen` from the controller. The worker writes logs, checkpoint receipts, hardware telemetry and an append-only ledger outside Git, then uploads, verifies and deallocates. Read the downloaded `diagnostic_status_screen.json`, train/evaluation logs and stability/incident files after the H100 is off. Before the next trial, complete [the diagnostic review template](notes/REVIEW_TEMPLATE.md), including benefits, regressions, surprises, missing telemetry and a decision. Do not replace the layer/tensor-level review with an aggregate maximum or final loss. A crash is a recorded outcome and needs the same failure review; fix a trivial implementation error with a new commit and a new trial ID.
5. If at least one candidate merits a longer comparison, first resume the baseline with the Azure-cycle command's `--stage full`, then continue promising **or uncertain** candidates with `--stage full` on each exact candidate commit. Each stage is a separate boot and verified shutdown. The baseline and candidate must be compared at the same stage. If no candidate merits continuation, leave the baseline at its screen checkpoint and preserve the budget. A candidate that improves English loss but learns more slowly, clips heavily, suppresses a branch, consumes much more memory or loses substantial throughput remains a tradeoff, not an automatic winner. Near ties are unresolved. If the change affects model arithmetic or attention behavior, check native/reference parity and the relevant length-boundary tests before interpreting quality.
6. After matched dense full results, decide whether ternary conversion could reverse the ranking. Anticipate the possible QAT cost while planning full continuations so the pair can fit inside the cap. If the proposal note gives a specific mechanism and relevant evidence, run the Azure-cycle command with `--trial-id baseline --stage qat_probe --qat-rationale "<specific reason and predicted signal>"` on the baseline commit, then repeat with the candidate ID and its commit. Compare the immediate conversion shock, short-QAT English loss, QAT penalty, optional tasks and incidents. Do not use an unmatched QAT trial as a win, and do not discard a dense improvement solely on a short QAT probe. If no QAT-sensitive reason exists, record `QAT probe: skipped` with the reason.
7. Keep an append-only evidence trail. Retain rejected branches and receipts; do not reset away failed experiments or rewrite published commits. Update the diagnostic review after full and QAT stages. Advance the incumbent only after a full comparison of English quality and learning curve, numerical behavior, measured cost, parameter count and implementation complexity, including positive and negative per-layer and per-parameter findings. A nonfinite failure is disqualifying. Clipping, attention concentration and residual scale are diagnostics requiring comparison with baseline and functional evidence; do not invent a universal hard threshold. Keep a small Pareto shortlist when trade-offs or uncertainty remain. Use each material surprise or unexplained failure to formulate a new search question; inspect relevant literature and implementations before forming the next mechanism-based hypothesis.
8. Stop at the GPU-hour cap or if the remaining budget cannot support a meaningful continuation. Report exact completed trials, GPU-hours, missing benchmarks, and the shortlist with uncertainty. Recommend which finalists need cross-domain, larger-width, inference-latency and longer ternary-QAT transfer checks before production selection. Do not silently turn stage one into optimizer tuning or kernel optimization.

## Operational rules

- If an English development task suite is supplied, keep its items and hashes fixed for all full evaluations. Keep untouched final tasks outside the loop. Do not tune on them. Check Indic/code/math transfer only for finalists in a separate campaign.
- Record citations or repository revisions for borrowed methods. Distinguish an established paper result from a Terminus hypothesis. Verify licenses before importing code.
- The model source may span multiple files, unlike Karpathy's `train.py`. The protected `train.py` here is a runner wrapper; the agent-editable architecture is `candidate.json` and the permitted model files.
- A fixed-time five-minute trial would change the number of tokens seen. Compare quality and learning at matched tokens; separately compare measured training speed, peak memory and full GPU cost. Do not declare a winner on only one axis.
- The campaign has a hard spending cap. When the human asks to stop, stop proposing/launching trials; safely interrupt any active worker, preserve its checkpoint, and verify its archive before shutdown. The Azure worker deallocates only after a fresh download and SHA-256 verification of its trial tree. A failed archive leaves the VM on for recovery; treat that as an urgent operational problem, not permission to start another trial. Do not claim remote safety from a successful upload command alone.
