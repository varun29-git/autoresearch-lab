The model remains the 25-layer, 1,500,456,496-parameter stack-004 with 4K context, 65K vocabulary, Peri-LN and value residual. Dense training is this campaign's subject. QAT is a later stage.

The production objective is at least **1.5 trillion**, ideally **2 trillion**, unique loss-bearing tokens in **6,000 aggregate H100 GPU-hours**, including QAT and operational overhead, on 32 GPUs. The absolute no-overhead requirement is 69,444 / 92,593 tokens/s **per GPU**. The previous selected dense stack delivered about 41,075 tokens/s in an 80-update soak on one H100 NVL; the full JSON receipt for that soak was not copied off the VM, so use the three complete 20-update candidate/reference pairs (40,996 versus 36,723 tokens/s on average) as the independently inspectable anchor. These numbers are starting evidence, not a production forecast. At 41,075 tokens/s, even perfect scaling yields only 887B dense tokens in the production budget.

Your research allocation is **five cumulative H100 VM-on hours**. Boot, compilation, tests, idle time while allocated, archive and shutdown consume that allocation. `research.speed_session` enforces 18,000 cumulative seconds with a VM-side cutoff timer; use a fresh external control root and ledger for this campaign. The human authorizes the paid start once. After that authorization, choose, code, stage, test, reject, revise and restart without asking between experiments. ## The Karpathy-style loop

The program, valid-token counter, tokenizer, real data manifest, full-update timer, reference model shape and production budget stay fixed. The editable surface is candidate model execution: kernels, operand storage/layout, optimizer execution, attention, exact loss, memory schedule and trainer scheduling. You may explore novel algebraic decompositions, new kernel architectures and controlled numerical representations. Keep depth, width, context, vocabulary, Peri-LN, value residual and all loss-bearing tokens. Class `E` preserves the selected optimizer and numerical training computation. A separately labeled class `N` may change precision or optimizer mathematics, but needs matched-token quality and gradient evidence before its speed can count as a win. A different global update batch or schedule is also a separately labeled `N` trial with matched-token quality, never a direct same-contract speed comparison. Never silently change the benchmark or skip work.

One trial is one stated mechanism on one immutable commit. Its primary score is `valid_tokens / synchronized full_optimizer_update_seconds` on the one H100 with real staged data. Hard gates are finite updates, numerical equivalence or declared numerical quality, unchanged unique-token accounting, and peak allocated memory within the production-relevant envelope (74 GB until actual production SKU is supplied). Preserve both speed and memory on the Pareto frontier; report total billed VM time separately. A microbenchmark guides a hypothesis but never wins a trial by itself.

Repeat this cycle until the five-hour cap or a genuinely proven production goal:

1. Read the latest complete receipts and the profiler's **exposed whole-update** time. Rank hypotheses by credible saved milliseconds per update divided by implementation and GPU-test time. Start with weight-gradient/other GEMMs and hybrid attention, then FP8 conversion and the exact vocabulary head. Re-rank after each meaningful win. [PENDING_5H.md](docs/speed/PENDING_5H.md) lists every unfinished original direction and new high-upside paths; it is a menu to attack the actual bottleneck, not a mandatory order. Give every P0/P1 direction either a measured trial or a quantified reason it cannot matter before calling the dense search saturated; a failed config toggle does not falsify an entire direction.
2. Before paid GPU time, have the first high-value candidate and the next fallback ready. Use focused local correctness checks. While the VM runs a useful test, prepare the next candidate. Do not keep it powered for reading, paperwork or purposeless utilization. Deallocate with `--reason idle` only when the coding gap exceeds measured shutdown + boot + restage cost, then resume from the same ledger.
3. Commit a candidate. Run a brief isolated parity check if it changes a kernel, then run `scripts/s0_block.py` for 1–2 warmup and 2–4 measured **complete** updates at the locked token stream and 524,288 valid tokens/update. Compare with an interleaved unchanged incumbent block when clocks/drift or a close result warrant it. A first speed screen should take minutes, not a 15–20-minute ritual. Use 20-update paired blocks only for a plausible winner; one longer soak is enough for a final candidate.
4. Immediately copy each full `block.json` and concise stdout to the external local results directory, verify its SHA-256, and append one row to `results.tsv`. Do this before deallocation; the prior 80-update soak lost its full local receipt. Keep all rejected commits and append-only results. Never place corpora, checkpoints, trial results or credentials in Git.
5. Keep a candidate only when the whole-update gain exceeds noise **and** the appropriate correctness gate passes. If two ideas fail or gains flatten, revisit the cost map, derive a bound for the dominant time, inspect current production implementations and relevant mathematics, then propose a new mechanism. You are free to invent a better framework for these exact operations. Do not take another system's throughput as a ceiling or assume an attractive kernel benchmark transfers to the full update.
6. After a material change, update the physics gap and 32-GPU transfer calculation from the new sustained receipt. Use explicit communication, QAT and downtime scenarios. One GPU cannot certify 32-GPU scaling or the production token objective.

A `results.tsv` row has this tab-separated schema:

`trial_id  parent_commit  candidate_commit  class  hypothesis  expected_saved_ms_per_update  measured_updates  valid_tokens  seconds  tokens_per_second  peak_allocated_bytes  parity_or_quality  decision  cumulative_vm_seconds  receipt_sha256`

The TSV and full receipts live under the **new external control root**. Record `failed`, `rejected`, `kept` and `unresolved` outcomes, including compile errors and negative trials. Never compare a candidate with a different shape, token count or update rule without labeling the changed contract. If a change needs a new numerical training contract, give it a separate comparison against the same-token incumbent; do not rewrite old rows.

## Stop and report

Do not use `close --reason goal` merely because the dense round is complete or a short-run speed number looks good. The production objective is only proven after dense and QAT rates, 32-GPU scaling, quality and operational costs fit 6,000 H100-hours. In this one-GPU dense pass that proof is unlikely; normally use the full five-hour budget for meaningful tests, pausing with `idle` if a new candidate needs offline development. Use `budget` at the cap. The cutoff timer is the last-resort guard if the agent disconnects.

At the end, deallocate and confirm Azure reports `PowerState/deallocated`. Report the best complete-update rate, valid tokens, memory, numerical/quality evidence, cumulative VM-on hours, all negative trials, the remaining milliseconds by component, and the honest dense-plus-QAT/32-GPU gap to 1.5T and 2T. A five-hour cap can bound the research; it cannot guarantee the production target. Never claim success from a projection alone.
