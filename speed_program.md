## What success means

Optimize **quality-qualified, loss-bearing training tokens per aggregate billed GPU-second**. Report dense and QAT separately and combine by token-weighted **time**, not arithmetic mean speed. A high TFLOP/s number, lower allocated memory, a fast forward pass, or a single lucky run is not success. Report the remaining gap against the physical bounds and the 6,000-hour projection after every accepted change.

The 32-GPU targets before overhead are 2.222M tokens/s for 1.5T and 2.963M for 2T. Reserve overhead explicitly. With an illustrative 10% unavailable-time allowance, useful running throughput must be 2.469M / 3.292M tokens/s. A single-GPU result must additionally survive communication overhead. Keep assumptions and measured quantities separate.

Do not promise that research must discover a 2.5× improvement. Seek it aggressively; demonstrate what is achieved. If measurements invalidate feasibility, report the shortfall and its physical cause. Do not change the denominator, model, data, or quality standard to create a win.

## Hard invariants

- Keep 25 layers, the frozen width/FFN/head dimensions, all learned Peri-LN output gains, all learned Q/K gains, both value-residual coefficients in each layer ≥1, and the complete gradient path back to layer 0. Keep residual placement, epsilon, RoPE, attention scale, exact causal/local masks, tied embeddings, and the 65,536-token vocabulary.
- No skipped layers, smaller windows/context, low-rank replacements, parameter freezing, model sparsification, token dropping, sampled softmax, cheaper data mixture, or claiming padded/replayed/rematerialized tokens as new training. No quality-for-speed shortcut disguised as a kernel optimization.
- Freeze optimizer **mathematics**, logical matrix groups, hyperparameters, schedule in tokens, global batch, initialization/checkpoint, tokenizer, data stream, evaluation and QAT recipe. You may change their implementation when equivalence is proved. Microbatch and accumulation may change together while preserving the exact global update and sample order.
- Distinguish class E (equivalent computation, floating-point evaluation order may differ) from class N (new numerical representation such as FP8 attention/head or compressed saved activations). Class N requires a separately versioned numerical subcampaign, stronger matched quality evidence, and an explicit error budget. No silent switch to a different optimizer, ternary estimator, quantization scale, or arithmetic recipe.
- Preserve reference code and rejected experimental branches. Never reset/rebase away a published experiment. Every attempted paid trial, crash, timeout and archive failure has an external append-only receipt. No datasets, weights, traces, per-item evaluations, trial records or credentials in Git.

## The bounded autonomous loop

Once the human starts the campaign, continue within its authorization and cap without requesting approval after every trial.

1. **Observe.** Read the last full-update trace, phase-specific memory ledger, every incident and the unresolved-cost table. Categorize exposed time into GEMM, attention, vocabulary loss, pointwise/casts, optimizer, host/data and later communication. An unexplained gap is a research question. Inspect the lowest useful level; do not choose an idea because its title sounds impressive.
2. **Derive.** Pick the next experiment by recoverable **whole-update** time and information gained per research hour. Calculate Amdahl's ceiling, bytes removed, FLOPs added, live tensors, register/shared-memory needs and expected launch count. State what must appear in the trace if the hypothesis is true. Search primary sources and competing implementations as the question demands; the atlas is a starting set, not an exhaustive menu. Verify licenses and pin any imported revision.
3. **Predeclare.** Write a proposal using the template. Specify baseline, class E/N, phase, exact shapes, implementation boundary, unchanged invariants, minimum effect, numerical checks, budget, disconfirming signal and artifact IDs. A coherent kernel package may require several coordinated edits; isolate its cause with a reference mode or ablation.
4. **Implement and commit.** Work from an immutable incumbent in a fresh `speed/trial-<id>` branch. Add the simple reference and relevant gradients first. Check source/contract changes. Commit code and proposal before launch. No changing benchmark lengths, tolerances, input samples or scorer after seeing candidate results.
5. **Screen cheaply.** Run numerical gates, then exact-shape component tests. Stop immediately if the predicted total benefit is too small or memory cannot fit production. A component win earns a full-update comparison; it never becomes the incumbent by itself. Compile and autotune once, then use balanced AB/BA paired full-update blocks with fresh equivalent state.
6. **Review.** Use `python3 -m speed_research analyze` on externally stored evidence. Review raw paired blocks, not just its decision. Explain gains, losses, numerical differences, memory changes, amortization and anomalies. `screen_pass` is only a speed-screen result. Failed quality, missing lambda/QK gain gradients, detached V₁, stale FP8 caches or a dishonest timing boundary disqualify the candidate.
7. **Confirm.** Spend longer quality/soak runs only on promising finalists and unresolved high-value hypotheses. Require new confirmation blocks to defeat selection bias; test dense, transition and QAT; verify uninterrupted versus resumed training. Combine compatible winners in pairs before stacking everything. Reprofile every accepted combination; do not multiply isolated speedups.
8. **Update the incumbent.** Only advance after the relevant numerical, quality and speed gates all pass. Record remaining 1.5T/2T gaps under conservative phase/scaling/overhead scenarios. Keep a robust fallback and a Pareto alternative when a faster candidate has unresolved memory or numerical risk.
9. **Stop intelligently.** Stop on human request, cap, insufficient budget for the next meaningful gate, or diminishing expected return. A failure is evidence. Archive, independently verify artifacts, and follow the human's shutdown procedure. Report exact charges including failures and idle/setup time. Never buy another GPU to rescue a research plan.

## Allocation, exploration and escalation

The human supplies the cap; suggested allocation is 15% S0/reference/profiling, 40% component/full-update experiments, 30% paired quality/soak, 15% reserve and confirmation. Reallocate based on measured uncertainty, never overspend. Reserve enough to compare finalists against the reference. Keep a research-hour account separate from the 6,000 production hours.

Start with tensor-lifetime/cast/layout diagnosis, then the dominant measured opportunities. Budget a minority of exploratory effort for the atlas's higher-risk coupled execution ideas. Kill an idea when a cheap diagnostic bounds its gain below relevance. Conversely, do not dismiss a substantial implementation because it is unfamiliar if the math, trace and expected end-to-end saving justify it.

Single-GPU-only research ends with a **qualified implementation plus a 32-GPU acceptance package**, not a fabricated distributed result. Prepare exact distributed test commands/configs and a first-production-hour rollback decision. The owner authorizes that later deployment. If the network or production SKU remains unspecified, provide a sensitivity range and name the missing input.
