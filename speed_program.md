# Kimi K3: continuous stack-004 speed research

Speed up the **same** 25-layer, ~1.5B-parameter stack-004 model. **This three GPU-hour research pass is dense-only on one H100. Do not run, tune or benchmark QAT in it.** The later production objective remains at least 1.5T, ideally 2T, unique training tokens across dense training and ternary QAT in 6,000 aggregate H100 GPU-hours on 32 GPUs. Keep the layer count, width, context, vocabulary, Peri-LN, value residual, optimizer mathematics, and real token count. Do not buy speed by skipping computation or silently weakening quality.

## Run the loop

Before the one authorized GPU start, have the model/data/config and a few high-value first experiments ready. After authorization, **start the VM yourself and keep running experiments continuously**. One authorization covers choosing, coding, staging, measuring, rejecting, revising and retesting ideas, plus deallocation/restart within the cap. Do not stop to ask permission between experiments. The old `research.azure_speed_worker` runs one S0 plan and shuts down; **do not use it as the continuous loop**. Use `research.speed_session` for VM lifecycle and `scripts/s0_block.py` for complete-update timing.

1. Establish a dense same-shape reference: one or two warmup updates, then two to five measured **complete optimizer updates**. Record unique valid tokens, elapsed time, device memory, setup time, commit, and total VM-on time. Use a brief profiler capture only to locate exposed time. A CPU result is not an H100 speed result.
2. Maintain a short ordered queue of hypotheses, each with expected whole-update saving, implementation/test cost, and quality risk. The [physics sheet](docs/speed/PHYSICS.md), [idea atlas](docs/speed/EXPERIMENTS.md) and [production implementation research](docs/speed/PRODUCTION_IMPLEMENTATIONS.md) inform choices, but profiling and new ideas can change the order. External designs are ideas, not throughput ceilings. Attack the dominant exposed cost, not the most fashionable kernel. Keep a running throughput/memory/correctness Pareto frontier.
3. While the VM is on, move directly from one measured experiment to the next. Write or stage the next candidate while a useful GPU test runs when possible. Do CPU coding and focused tests as needed, but do not repeatedly stop the VM for ordinary analysis. If a new candidate is not ready, use the GPU for a useful dense matched repeat or short profile; do not run purposeless work to claim utilization.
4. Use short matched reference/candidate screens first. Reject a clear loser quickly; repeat close/noisy results. Give longer dense numerical, quality and sustained-speed tests only to plausible winners. A change to numerical precision requires dense gradient and matched-token quality checks. Preserve failures and results in an append-only log outside Git.
5. After each result, recompute the remaining **VM-on** budget and choose the next experiment by expected production benefit per research minute. Compare continuing on the live VM with deallocating and later restarting: deallocate for a real idle interval only when its expected duration exceeds measured shutdown + restart + restaging overhead and the remaining budget still supports another useful trial. Otherwise keep the GPU on. A deallocation pauses the campaign; it does not reset the three-hour total.

For this pass, maximize **validated dense tokens/s on one H100** at the production-relevant per-rank workload. Do not stop merely because a nominal token-rate target is crossed. Stop early only if measurements and hardware bounds show no material recoverable whole-update time remains; otherwise use the three-hour cap. At the end, deallocate and report the best dense frontier and unsolved bottleneck. Do not silently extend the cap. The VM cutoff timer is a fallback if the agent hangs; proactively finish and deallocate with enough time for Azure shutdown.

Build a 32-GPU transfer model during this dense pass: use the actual per-rank local workload; inventory persistent state, activation memory, gradient-bucket readiness and unavoidable communication bytes; model all-reduce overlap and topology sensitivity using explicit efficiency ranges. The one-GPU trace can reveal what may transfer but **cannot validate 32-GPU scaling**. State which distributed measurements will be required later. QAT speed and quality are also separate later gates, so a dense-only projection cannot prove the full production token objective.

The first speed screen needs neither six paired minute-long runs nor a full checkpoint or production preflight. The normal production trainer keeps its preflight. Measure **billed VM-on time separately from timed training**; VM boot, JIT, idle thinking, uploads and shutdown all count against the three-hour research cap.

`research.speed_session` has `open`, `status`, `stage`, `exec`, and `close` actions. Its ledger must live outside Git, results must stay on a persistent disk, and `open` is a paid action: invoke it only after the one-time campaign authorization. Use `close --reason goal` only for the physics-backed dense saturation criterion above, `close --reason budget` at the cap, or `close --reason idle` only for a cost-justified pause. The [README](docs/speed/README.md) shows the commands. Run continuously until one of those terminal conditions; an agent conversation ending is not a valid reason to leave the VM billed.
