# Kimi K3: stack-004 dense speed autoresearch, five-hour campaign

This worktree starts from `1e8c0a4`, the E3 packed Q/K, E4 value-mix, E9 batched-Muon implementation. Improve this implementation; do not restart from the old architecture or mistake the rejected E2 fusion for a winner. The model remains the 25-layer, 1,500,456,496-parameter stack-004 with 4K context, 65K vocabulary, Peri-LN and value residual. Dense training is this campaign's subject. QAT is a later stage.

The sole objective of this campaign is to maximize **validated dense full-update throughput on one H100 NVL**, while preserving the selected stack-004 model and its training computation. The previous selected dense stack delivered about 41,075 tokens/s in an 80-update soak; its full JSON receipt was not copied off the VM, so use the three complete 20-update candidate/reference pairs (40,996 versus 36,723 tokens/s on average) as the independently inspectable anchor. These numbers are starting evidence, not a throughput ceiling. QAT, distributed scaling and production-budget modeling are outside this campaign.

Your research allocation is **five cumulative H100 VM-on hours**. Boot, compilation, tests, idle time while allocated, archive and shutdown consume that allocation. `research.speed_session` enforces 18,000 cumulative seconds with a VM-side cutoff timer; use a fresh external control root and ledger for this campaign. The human authorizes the paid start once. After that authorization, choose, code, stage, test, reject, revise and restart without asking between experiments. No cloud VM is started by merely reading or preparing this worktree.

## The Karpathy-style loop

The program, valid-token counter, tokenizer, real data manifest, full-update timer and reference model shape stay fixed. The editable surface is candidate model execution: kernels, operand storage/layout, optimizer execution, attention, exact loss, memory schedule and trainer scheduling. You may explore novel algebraic decompositions, new kernel architectures and controlled numerical representations. Keep depth, width, context, vocabulary, Peri-LN, value residual and all loss-bearing tokens. Class `E` preserves the selected optimizer and numerical training computation. A separately labeled class `N` may change precision or optimizer mathematics, but needs matched-token quality and gradient evidence before its speed can count as a win. A different update batch or schedule is also a separately labeled `N` trial with matched-token quality, never a direct same-contract speed comparison. Never silently change the benchmark or skip work.

One trial is one stated mechanism on one immutable commit. Its primary score is `valid_tokens / synchronized full_optimizer_update_seconds` on the one H100 with real staged data. Hard gates are finite updates, numerical equivalence or declared numerical quality, unchanged unique-token accounting, and measured device use that fits the actual GPU with enough headroom for repeatable full updates. The old 74 GB production-planning cap is not a gate for this H100 NVL run. Preserve both speed and memory on the Pareto frontier; report total billed VM time separately. A microbenchmark guides a hypothesis but never wins a trial by itself. Compare improvement with the **single-GPU** exposed-time and hardware bounds, not with other implementations' headline rates.

Repeat this cycle while meaningful single-GPU experiments remain and cumulative VM-on time is below five hours:

1. Read the latest complete receipts and the profiler's **exposed whole-update** time. Rank hypotheses by credible saved milliseconds per update divided by implementation and GPU-test time. Start with weight-gradient/other GEMMs and hybrid attention, then FP8 conversion and the exact vocabulary head. Re-rank after each meaningful win. [PENDING_5H.md](docs/speed/PENDING_5H.md) lists every unfinished original direction and new high-upside paths; it is a menu to attack the actual bottleneck, not a mandatory order. Give every P0/P1 direction either a measured trial or a quantified reason it cannot matter before calling the dense search saturated; a failed config toggle does not falsify an entire direction.
2. Before paid GPU time, have the first high-value candidate and the next fallback ready. Use focused local correctness checks. While the VM runs a useful test, prepare the next candidate. Do not keep it powered for reading, paperwork or purposeless utilization. Deallocate with `--reason idle` only when the coding gap exceeds measured shutdown + boot + restage cost, then resume from the same ledger.
3. Commit a candidate. Run a brief isolated parity check if it changes a kernel, then run `scripts/s0_block.py` for 1–2 warmup and 2–4 measured **complete** updates at the locked token stream and 524,288 valid tokens/update. Compare with an interleaved unchanged incumbent block when clocks/drift or a close result warrant it. A first speed screen should take minutes, not a 15–20-minute ritual. Use 20-update paired blocks only for a plausible winner; one longer soak is enough for a final candidate.
4. Immediately copy each full `block.json` and concise stdout to the external local results directory, verify its SHA-256, and append one row to `results.tsv`. Do this before deallocation; the prior 80-update soak lost its full local receipt. Keep all rejected commits and append-only results. Never place corpora, checkpoints, trial results or credentials in Git.
5. Keep a candidate only when the whole-update gain exceeds noise **and** the appropriate correctness gate passes. If two ideas fail or gains flatten, revisit the cost map, derive a bound for the dominant time, inspect current production implementations and relevant mathematics, then propose a new mechanism. You are free to invent a better framework for these exact operations. Do not take another system's throughput as a ceiling or assume an attractive kernel benchmark transfers to the full update.
6. After a material change, briefly reprofile the same one-GPU full update, update the exposed-time and hardware-bound gap, and reprioritize the next experiment. Do not spend this research allocation on 32-GPU transfer or QAT work.

A `results.tsv` row has this tab-separated schema:

`trial_id  parent_commit  candidate_commit  class  hypothesis  expected_saved_ms_per_update  measured_updates  valid_tokens  seconds  tokens_per_second  peak_allocated_bytes  parity_or_quality  decision  cumulative_vm_seconds  receipt_sha256`

The TSV and full receipts live under the **new external control root**. Record `failed`, `rejected`, `kept` and `unresolved` outcomes, including compile errors and negative trials. Never compare a candidate with a different shape, token count or update rule without labeling the changed contract. If a change needs a new numerical training contract, give it a separate comparison against the same-token incumbent; do not rewrite old rows.

## Stop and report

Do not use `close --reason goal` merely because one subround is complete or a short-run speed number looks good. An early `goal` stop requires a measured single-GPU throughput plateau against credible hardware and exposed-time bounds, with every remaining high-upside direction tested or quantitatively ruled out. Otherwise use the five-hour budget for meaningful experiments, pausing with `idle` if a new candidate needs offline development. Use `budget` at the cap. The cutoff timer is the last-resort guard if the agent disconnects.

At the end, deallocate and confirm Azure reports `PowerState/deallocated`. Report the best complete-update rate, valid tokens, memory, numerical/quality evidence, cumulative VM-on hours, all negative trials, the remaining milliseconds by component, the single-GPU physical bounds, and the next highest-upside experiment. A five-hour cap bounds the search; do not claim saturation from a short benchmark or an unmeasured projection.
